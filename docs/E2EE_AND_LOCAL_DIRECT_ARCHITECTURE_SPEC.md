# ReDash 下一代架构演进方案：端到端加密 (E2EE) 与局域网直通 (Local-First Direct)

> **目标**：彻底终结“中心化明文代理”的安全缺陷与流量瓶颈，将 ReDash 打造为与 **Orca / Tailscale** 齐平的**零信任盲中继 (Zero-Trust Blind Relay) + 局域网无缝直通 (Local Direct-Path)** 现代分布式架构。

---

## 一、架构愿景与拓扑演变

### 1. 现状痛点（中心化明文网关）
- **中心化特权风险**：Hub 掌握所有明文终端流、控制命令与返回结果。一旦公网 Hub 节点遭受渗透，攻击者可窥视所有纳管主机的全部凭据与会话。
- **流量强行绕路**：处于同一局域网的客户端与受控节点，数据仍然必须先流向公网 Hub 再流回，造成昂贵的云端带宽浪费与不必要的网络延迟。

### 2. 演进后的新拓扑架构

```
                     ┌──────────────────────────────────────────────┐
                     │          ReDash Hub 控制面与盲中继             │
                     │                                              │
                     │  - 控制面元数据注册表 (Node Registry)          │
                     │  - 离线健康哨兵 (Health Sentinel / Webhook)  │
                     │  - 哑管道密文转发器 (Blind Cipher Relay)       │
                     └──────────────────────────────────────────────┘
                                     ▲                     ▲
                   (公网时仅盲转密文) │                     │ (公网时仅盲转密文)

│                         │                          │                          │
```

## 二、核心技术模块设计

### 模块 A：真·端到端加密协议 (E2EE - End-to-End Encryption)

#### 1. 密钥协商生命周期 (X25519 + HKDF)
客户端发起任意治理操作或 WebTTY 会话时，动态生成一次性临时密钥对（Ephemeral Keypair），通过 Hub 交换公钥，推导出两端独有的会话对称密钥：

```
客户端 (Client)                                          受控节点 (Agent)
      │                                                         │
      │ 1. 生成临时密钥 (E_client_priv, E_client_pub)           │
      │    使用长期私钥对握手包签名 (ED25519 Signature)         │
      │                                                         │
      │──── E2eeHandshakeInit(E_client_pub, Nonce, Sig) ───────>│ (通过 Hub 盲转发)
      │                                                         │
      │                                2. 验证 Client 长期公钥签名
      │                                   生成临时密钥 (E_agent_priv, E_agent_pub)
      │                                   计算共享密钥 S = ECDH(E_agent_priv, E_client_pub)
      │                                   衍生会话密钥 K_session = HKDF(S, Salt)
      │                                                         │
      │<─── E2eeHandshakeAck(E_agent_pub, AuthTag) ─────────────│ (通过 Hub 盲转发)
      │                                                         │
3. 计算共享密钥 S = ECDH(E_client_priv, E_agent_pub)            │
   衍生同一会话密钥 K_session = HKDF(S, Salt)                   │
   校验 AuthTag                                                 │
      │                                                         │
      │═════════════════════════════════════════════════════════│
      │  正式数据通道建立：所有帧均封装为 ChaCha20-Poly1305 密文  │
      │═════════════════════════════════════════════════════════│
```

#### 2. 数据报文封装规范
```rust
/// 加密后的通用数据封包（Hub 只能看到外层元数据，内容完全不透明）
pub struct EncryptedEnvelope {
    pub session_id: String,     // 会话路由标识
    pub seq_num: u64,           // 序列号（单调递增，防乱序重放）
    pub nonce: [u8; 12],        // 一次性随机随机数
    pub ciphertext: Vec<u8>,    // 加密密文 (ChaCha20)
    pub auth_tag: [u8; 16],     // 消息完整性认证标签 (Poly1305)
}
```

#### 3. Hub 的角色降级：从“全知代理”到“哑管道 (Blind Relay)”
- `redash-server` 仅通过 `session_id` 做哈希匹配与转发，代码中彻底移除对终端字符或结果 Payload 的反序列化逻辑。
- 即使 Hub 服务器被中间人监听或系统被物理控制，泄露的也仅是无法破解的高强度加密噪声。

### 模块 B：局域网就近直通 (Local-First Direct Path)

借鉴 Orca 与 Tailscale 的优势，实现网络环境感知与智能路径优选。

#### 1. Agent 本地发现广播 (mDNS / Bonjour)
- `redash-agent` 启动时，除了向公网 Hub 建立出站 WebSocket，同时在本地监听一个回环或内网端口（仅绑定内网 IP），并通过 mDNS 对外广播：
  - **服务标识**：`_redash._tcp.local`
  - **TXT 属性**：`node_id=<ID>`, `fingerprint=<ED25519_PUBKEY_HASH>`, `port=<PORT>`

#### 2. 双路径并行竞速算法 (Happy Eyeballs for ReDash)
客户端打开终端或发起指令时，并发触发路径探测：
1. **通道 A（局域网直通探针）**：利用 mDNS 解析出的 `local_ip:port` 发起轻量 TCP 握手探针（超时时间设定为 50ms）；
2. **通道 B（公网 Hub 盲中继）**：向已连接的 Hub 发起中继请求；
3. **竞速选择**：
   - 若局域网探针在 50ms 内握手成功，**立即升级为主通信链路**（延迟 < 1ms，耗费 0 公网流量）；
   - 若局域网探针超时（说明客户端在外网出差、或跨子网无法直连），**无缝回退走 Hub 盲中继**。

---

### 模块 C：会话保活与断线重连 (Session Resilience / Bridge 模式)

借鉴 Orca 的 `relay.sock` 设计：
1. **PTY 生命周期解耦**：
   - Agent 内部维护独立的 `PtySupervisor`，与网络 WebSocket 解耦。
   - 当遇到 Wi-Fi 切换、网络波动或客户端暂时退入后台时，底层 Shell 进程**坚决不杀死**，终端输出写入本地环形回退缓冲区（Ring Buffer，保留最新 500 行）。
2. **快速会话重附加 (Re-attach)**：
   - 客户端网络恢复后，带上 `session_id` 与最后的 `seq_num` 重新建立 E2EE 握手；
   - Agent 瞬间重附加到原 Shell 会话并回放断线期间的缓冲流，用户感觉不到任何会话中断。

## 三、分阶段工程实施路线图 (Phase 1 ~ Phase 4)

| 阶段 | 核心任务 | 交付成果与验收标准 | 优先级 |
|---|---|---|---|
| **Phase 1: 数据面 E2EE 改造** | 1. 在 `redash-types` 中定义 E2EE 协议包结构<br>2. 引入 `chacha20poly1305` 与 `x25519-dalek`<br>3. 客户端与 Agent 实现透明加解密通道<br>4. Hub 降级为盲转发 | • WebTTY 终端 I/O 全链路加密传输<br>• Hub 内存与日志中无法还原出任何明文指令或密码 | **P0** |
| **Phase 2: 局域网 mDNS 直连** | 1. Agent 增加轻量 mDNS 广播与本地监听<br>2. 客户端实现 Happy Eyeballs 双径竞速<br>3. 本地直连通道接入相同的 E2EE 握手认证 | • 同 Wi-Fi 下打字延迟降至 < 2ms<br>• 大文件传输/滚屏时 Hub 服务器流量为 0 | **P1** |
| **Phase 3: 断线无损重连 (Bridge)** | 1. PTY 与网络连接生命周期分离<br>2. 环形终端回放缓冲区 (Ring Buffer)<br>3. 客户端网络切换断线重连机制 | • 笔记本合盖或切网后重新打开，终端依然存活<br>• 不丢失后台长驻任务 | **P2** |
| **Phase 4: 零配置扫码安全配对** | 1. 桌面端一键生成带公钥与信令地址的 QR 码<br>2. 移动端/新节点扫码一键完成公钥信任绑定 | • 彻底淘汰明文 Token 传参<br>• 获得极致开箱即用体验 | **P3** |

## 四、安全合规与威胁模型分析

| 攻击场景 | 传统中心化架构表现 | 演进后的 E2EE 架构表现 |
|---|---|---|
| **Hub 云服务器被黑客攻陷** | 致命。黑客截获所有节点明文 Shell 与主机凭据。 | **无影响**。黑客只能看到密文噪声，无法解密终端也无法伪造客户端签名指令。 |
| **恶意的伪造治理动作** | 依赖 Hub 的鉴权，Hub 沦陷即全军覆没。 | **免疫**。Agent 强制校验客户端长期私钥的签名，伪造包直接在 Agent 本地被丢弃。 |
| **局域网伪造节点 (ARP 欺骗)** | 局域网明文交互易被窃听。 | **免疫**。本地直通强制走基于公钥指纹的 E2EE 握手，中间人无法解密或欺骗。 |
