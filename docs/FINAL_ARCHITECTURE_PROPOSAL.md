# ReDash 下一代多模态控制面：最终架构方案规范 (方案 A：分权而治版)

> **定位**：对标 **Orca** 与 **T3 Code** 的工业级最佳实践，摒弃脆弱臃肿的重型 WebRTC 协议，采用**“数据面真·E2EE 盲中继 + 控制遥测面 7x24 守护 + 局域网直通”**的分权而治零信任现代运维架构。

---

## 一、架构定型与核心设计哲学

经过对主流开源方案（`stablyai/orca`、`pingdotgg/t3code`）的深度调研与技术论证，我们确立了以下核心共识：

1. **终端与运维流量本质极轻，无需搞过度设计的 P2P**：
   终端 PTY 字符、遥测指标与治理指令单次仅几百字节至几 KB，每月单节点流量只有几百 MB，根本不会打爆服务器带宽。强行在全端搞 WebRTC P2P，不仅带来庞大的 ICE/STUN 状态机，更会导致手机 App 切后台秒断闪退。
2. **中心化的真正威胁在于“明文窥视”，而非“流量转发”**：
   用户最担心的是公网 Hub 节点遭受渗透后，黑客窥视所有纳管主机的 Shell 击键、密码与执行结果。**解决的核心是端到端加密（E2EE），将 Hub 彻底降级为无法解密的“盲管道（Dumb Pipe）”**。
3. **方案 A（分权而治）：完美化解“E2EE 与自动化通知告警”的矛盾**：
   - **绝密数据面（100% E2EE 加密）**：终端 WebTTY 字符、密码输入、敏感命令回显、文件内容，Hub 绝对看不懂；
   - **系统遥测面（对 Hub 公开）**：CPU、内存、磁盘利用率及物理长连接心跳，由 Hub 负责 7x24 小时大盘展示、阈值计算与离线 Webhook 告警！

## 三、方案 A：数据敏感度与分级分权规范

| 维度 | 【绝密数据面】(100% 强制 E2EE) | 【系统控制与遥测面】(对 Hub 授权公开) |
|---|---|---|
| **承载内容** | • 终端 WebTTY 输入与输出字符流<br>• 用户敲击的 sudo 密码与环境变量<br>• 敏感运维脚本执行结果<br>• SFTP 远程文件读写流 | • 机器基础运维指标 (CPU/内存/磁盘利用率)<br>• 网络收发速率吞吐<br>• Docker 容器名与状态 (running/exited)<br>• 节点物理长连接心跳 (Ping/Pong) |
| **加密方式** | **X25519 协商 + ChaCha20-Poly1305 密文** | 标准 HTTPS / TLS 传输层加密 |
| **Hub 权限** | **彻底的“盲人”（Dumb Pipe）**，无法解密，仅依据 `session_id` 路由字节 | **完全解析**，用于聚合时序大盘与触发告警 |
| **核心职责** | 守住机密安全底线，防止公网 Hub 被攻破时泄密 | **7x24 小时离线监控哨兵与 Webhook 告警中心** |

## 四、四大核心技术基石

### 1. 真·端到端加密数据信封 (E2EE Envelope)
- **密钥协商**：两端利用已有的 ED25519 密钥派生 X25519，通过 ECDH 交换一次性 Ephemeral 密钥，生成会话对称密钥。
- **密文封包规范**：
  ```rust
  pub struct EncryptedEnvelope {
      pub session_id: String,     // 路由标识（Hub 仅依据此字段转发）
      pub seq_num: u64,           // 序列号（单调递增，防重放）
      pub nonce: [u8; 12],        // 一次性随机数
      pub ciphertext: Vec<u8>,    // ChaCha20 加密后的真实数据
      pub auth_tag: [u8; 16],     // Poly1305 消息认证标签（防篡改）
  }
  ```
- **Hub 角色蜕变**：Hub 彻底移除明文终端流的反序列化代码，变成纯密文盲中继。

### 2. Hub 7x24 小时自主监控与告警闭环
- **指标超限告警（`AlertMonitor`）**：Hub 后台常驻巡检，当任意节点 CPU > 阈值、内存 > 阈值、磁盘 > 阈值时，自动向配置的钉钉/企业微信/飞书/Webhook 发送富文本报警；
- **物理失联监控（`HealthSentinel`）**：基于长连接心跳。只要 15s 没心跳标记 `Stale`，30s 没心跳立即标记 `Offline` 并触发报警：`🚨 节点 [xxx] 失去长连接心跳，可能遭遇物理断电！`。

### 3. 局域网 mDNS 就近直连
- `redash-agent` 启动时除了向 Hub 注册，同时在本地监听并在局域网广播 `_redash._tcp.local`。
- 客户端在同网络下发起探测（超时阈值 50ms），探测通则直接建立本地直连，完全不消耗公网流量。

### 4. PTY 会话解耦与断线保活 (Bridge 模式，对标 Orca)
- 将 Agent 底层的 PTY 进程生命周期与网络 WebSocket 彻底解耦。
- 网络闪断或移动端切后台时，**不终止远程 Shell 进程**，终端输出写入本地环形回退缓冲区（Ring Buffer）；
- 网络重连后，客户端带上 `session_id` 和最后的 `seq_num` 重新附加（Re-attach），自动对齐遗漏字符，体验丝滑无感。

## 五、现场业务缺陷修复与交互安全加固

针对之前运行测试中暴露的实际问题，在本阶段一并做根治性加固：

1. **【释放端口】交互升级与防自杀拦截**：
   - 彻底移除硬编码 `port: 8080`；
   - 点击【释放端口】弹出轻量交互对话框，支持自定义输入目标端口（如 80, 443, 3000, 5432 等）；
   - **安全自杀拦截**：Agent 本地增加校验，禁止强杀自身长连接端口或 Hub 通信端口，防止误杀控制面。
2. **【Docker Chunked 解码修复】**：
   - 修复 Docker Socket HTTP/1.1 `Transfer-Encoding: chunked` 导致的 `invalid type: integer 4000` 反序列化警告。
3. **【桌面端启动异步平滑化】**：
   - 将 GPUI 的事件回调统一通过 `window.defer` 异步调度，杜绝实体更新锁冲突闪退。

## 七、方案核心价值总结

1. **安全达标**：核心终端 Shell 与敏感执行 100% E2EE 加密，彻底根除 Hub 单点泄密风险；
2. **运维能力完好无损**：保留 Hub 对遥测指标与物理心跳的 7x24 守护能力，告警不掉线；
3. **架构稳健轻量**：避免了 WebRTC 的复杂深坑，全端统一、代码轻巧、可维护性与稳定性达到 100%。
